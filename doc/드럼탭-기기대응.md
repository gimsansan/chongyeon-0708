# 드럼탭 기기 크기 대응 (2026-08-17)

기준 작업: 「기타 좌측 패널 세로 배치」(`doc/기타탭-UI개선.md` 6항) · 요청문은 `doc/탭-기기대응-요청문.md`.

대상은 **세로 5개 크기(320 / 360 / 375 / 393 / 800dp)** 다.
화면 방향은 건드리지 않기로 했으므로 가로(829×393)는 이번 범위 밖이다.

---

## 1. 이 탭이 쓸 수 있는 화면

| 항목 | 값 | 근거 |
|---|---|---|
| 하단 탭바 | 쓴다. `height: 64 + insets.bottom` | `app/(tabs)/_layout.tsx:66` |
| 탭바가 화면을 깎는가 | 깎는다 | `BottomTabView`가 탭바와 화면을 column으로 나란히 둔다 |
| 화면 안 insets | 원본 그대로 | `BottomTabView`에 `SafeAreaInsetsContext.Provider`가 없고 탭바만 `Consumer`로 쓴다 |
| 화면 방향 | 세로 (드럼 탭 자체 잠금은 없음) | `app.json`은 `"orientation": "default"`, 기타 탭이 이탈할 때 `PORTRAIT_UP`으로 잠근다 |

```
탭 화면 높이 = 창높이 − 64 − insets.bottom
스크롤 영역   = 탭 화면 높이 − 헤더(insets.top + 65, 태블릿 +67)
```

---

## 2. 고친 것 5가지와 그 근거

### 2-1. 하단 버튼이 화면 밖으로 밀려나던 문제

옛 식은 배경 이미지(`drum_m.webp`, 768×1152)의 레터박스 간격에서 버튼 위치를 역산했다.

```
bottom = insets.bottom + max(−70, round((간격 − 버튼높이)/2) − 45)
```

배경이 화면을 꽉 채워 간격이 0이 되면 offset이 −68~−70까지 떨어진다.
`창높이 ≥ 1.787 × 창너비 + 76` 을 만족하는 길쭉한 폰에서만 버튼이 보였고,
4:3·16:10인 태블릿은 크기와 무관하게 항상 잘렸다.

| 기기 | 옛 버튼 하단(바닥 기준) | 결과 |
|---|---|---|
| 320 × 568 | −20 | 46 중 26만 보임 |
| 360 × 640 | −20 | 52 중 32만 보임 |
| 375 × 667 (하단인셋 0) | −62 | 전부 화면 밖 |
| 393 × 829 | **+13** | 정상 |
| 800 × 1280 | −22 | 115 중 93만 보임 |

→ **393dp의 값 +13을 전 기기 공통 상수(`FIXED_BUTTON_BOTTOM`)로 고정**하고
레터박스 계산(`backgroundViewport` · `fixedButtonBottomOffset` 등)을 걷어냈다.

### 2-2. insets.bottom 이중 차감

탭바 높이에 이미 `insets.bottom`이 들어 있는데 `contentWrapper`가 한 번 더 뺐다.
제거해서 세로를 `insets.bottom`만큼 되찾았다(393에서 24dp).

### 2-3. 스크롤 봉쇄와 `marginTop: 150`

`contentContainerStyle`에 `flex: 1`이 있어 콘텐츠 높이가 뷰포트로 **고정**됐다.
넘쳐도 스크롤이 안 되고 잘렸다. 게다가 `sectionDrum.marginTop: 150`은
공간이 없어도 자리를 고집해 드럼을 위로 밀어냈다.

→ `flexGrow: 1`로 바꾸고(안전망), 위 여백을 **늘고 주는 칸 하나**로 교체했다.

```
paddingTop 20
drumTopSpacer   ← flex:1, minHeight:0, maxHeight:150  (유일한 가변 칸)
section(드럼)    ← flexShrink 0
drumBottomReserve = 버튼높이 + 26                      ← flexShrink 0
paddingBottom 30
```

### 2-4. `paddingBottom: 70` 제거와 좌표계 통일

`drumSetContainer`는 `height: drumSetSize`에 `paddingBottom: 70`이 있었다.
RN은 border-box라 **그림은 `S − 70`, 마커·캐릭터·스냅은 `S` 기준**으로 서로 달랐다.

```
가로 오차 = 35(2u − 1)   u=0.15에서 −24.5,  u=0.85에서 +24.5
세로 오차 = 70v          v=0.45에서 +31.5
```

이 오차는 dp 고정이라 그림이 작을수록 비율이 커졌다(320에서 14.4%, 태블릿 4.8%).
70은 이제 없어진 순환 버튼(`hideCycleButton`으로 꺼져 있던 `▶️1`) 자리였다.

→ 70을 없애고 **모든 좌표를 그림 기준 하나로 통일**했다.
크기식도 함께 바꿔야 세로가 실제로 회수된다. 상자 높이가 `0.9W`에서 `0.72W`로 줄어야
70dp가 돌아온다. 70만 지우면 그림만 25% 커지고 공간은 그대로다.

**393dp 화면을 그대로 재현하는 환산식** (S = 353.7, 그림 = 283.7, 가로 오프셋 35):

| 대상 | 옛 값 | 새 값 | 환산식 |
|---|---|---|---|
| 그림 크기 | `0.9W` 상자 − 70 | `0.72W` | 283.7 / 393 ≈ 0.72 |
| 캐릭터 크기 | `0.15 × 상자` | `0.1875 × 그림` | 0.15 × 353.7/283.7 |
| 스냅 반경 | `0.12 × 상자` | `0.1496 × 그림` | 0.12 × 353.7/283.7 |
| 마커 x | 상자 기준 | 그림 기준 | `x′ = 1.24674x − 0.12337` |
| 마커 y | 상자 기준 | 그림 기준 | `y′ = 1.24674y` |
| neutralOffset | 상자 기준 | 그림 기준 | `× 1.24674` (차이값이라 오프셋 없음) |

환산 결과 (`constants/drumLayouts.ts`):

| 레이아웃 | 악기 | 옛 좌표 | 새 좌표 |
|---|---|---|---|
| 2 | snare / kick | (0.37,0.25) / (0.57,0.35) | (0.338,0.312) / (0.587,0.436) |
| 3 | hihat / snare / kick | (0.19,0.15) / (0.33,0.35) / (0.55,0.45) | (0.114,0.187) / (0.288,0.436) / (0.562,0.561) |
| 4·5 | hihat / snare / kick / cymbal / tom | (0.15,0.2) / (0.27,0.35) / (0.46,0.44) / (0.85,0.2) / (0.55,0.15) | (0.064,0.249) / (0.213,0.436) / (0.450,0.549) / (0.936,0.249) / (0.562,0.187) |

검산(393dp, 2악기 snare): 옛 화면 위치 `0.37×353.7−15−35 = 80.9`,
새 위치 `0.338×283.0−15 = 80.6`. **0.3dp 차이**.

스냅 반경도 옛 `0.12×353.7 = 42.4dp` → 새 `0.1496×283.0 = 42.3dp`로 유지된다.
정답 판정 반경이 안 변한다는 뜻이다.

### 2-5. 헤더 중앙 배지 겹침

`headerCenter`가 `left:0 / right:0` 절대배치라 좌우 버튼 폭을 몰랐다.

| 기기 | 좌우 버튼 합 | 배지 폭 | 겹침 |
|---|---|---|---|
| 320 | 261 | 100 | 좌 31dp, 우 10dp |
| 360 | 261 | 100 | 좌 11dp |
| 375 | 261 | 100 | 좌 4dp |
| 393 | 261 | 100 | 없음 (5dp 여유) |

→ 절대배치는 유지하고 **좌우 버튼을 `onLayout`으로 재서 `left`/`right` 한계를 준다.**
flex 3칸으로 바꾸지 않은 이유는 좌우 칸 폭 차이로 393dp에서 배지가 몇 dp 움직이기 때문이다.

폭이 360dp 미만이면 여백만 줄여 배지 자리를 만든다(`isNarrowHeader`):
톱니 버튼 `marginHorizontal` 20→8, 듣기연습 `paddingRight` 14→8, 칩 `marginRight` 6→4,
배지 `paddingHorizontal` 14→8. 320dp에서 가용 63 → 95dp가 되어 배지(88)가 들어간다.

### 2-6. 태블릿 상한

| 대상 | 옛 값(800dp) | 상한 | 새 값 |
|---|---|---|---|
| 드럼 그림 | 650 | `DRUM_MAX_SIZE` 520 | 520 |
| 버튼 폭 | 181 | 132 | 132 |
| 버튼 높이 | 115 | 84 | 84 |
| 버튼 간격 | 308 | 225 | 225 |

버튼 간격에는 `화면폭 − 54 − 버튼폭×2` 상한도 걸었다. 320dp에서 두 버튼+간격이
오버레이 안쪽 폭을 1dp 넘던 것을 막는다.

## 3. 압축 모드

요청문대로 **창 높이에서 탭바를 빼서 추정하지 않고** 스크롤 영역을 `onLayout`으로 잰다.

```
compact = 실측높이 < 120(고정여백) + 20(여유) + 버튼자리 + 목표그림크기
고정여백: 일반 120 = 20+30 + 20+20 + 20 + 10
          압축  58 = 10+12 + 10+10 + 10 + 6
그림크기 = min(0.72W, 520, 실측높이 − 고정여백 − 버튼자리)
```

| 기기 | 실측 스크롤 높이 | 필요치 | 압축 |
|---|---|---|---|
| 320 × 568 | 391 | 442 | **켜짐** |
| 360 × 640 | 463 | 477 | **켜짐** |
| 360 × 800 | 623 | 477 | 꺼짐 |
| 375 × 667 | 518 | 490 | 꺼짐 |
| 375 × 812 | 605 | 490 | 꺼짐 |
| **393 × 829** | **652** | **505** | **꺼짐 (여유 147dp)** |
| 800 × 1280 | 1101 | 770 | 꺼짐 |

393dp는 147dp 여유라 어떤 상황에서도 압축이 켜지지 않는다.

## 9. 이번 세션 대화 기록 (결론에 영향을 준 것만)

전문이 아니라, **결정을 바꾼 대화와 틀렸다가 고친 것만** 남긴다.

### 9-1. 진단 먼저

> **사용자** — "드럼탭, 기기 크기별로 잘리는 요소가 있는지 계산해서 보고만 해. 고치지는 마. 이해?"

읽기 전용으로만 계산해서 보고. 여기서 나온 것:

- 잘리는 건 드럼 그림이 아니라 **하단 버튼**이다. 작은 기기에서 드럼은 잘리는 게 아니라 **위로 밀린다**.
- 393dp는 4dp 남기고 겨우 맞는 상태였다. 그래서 그 기기에서만 멀쩡해 보였다.
- 헤더 배지 겹침도 393dp만 여유 5dp로 아슬하게 통과하고 있었다.

### 9-2. 자산 크기 확인

> **사용자** — "@assets/images/drum_m.webp 너비 768px, 높이 1152px 이다."
> **사용자** — "last_22.png 부터 55까지 크기는 높이와 너비가 540px 이다."

배경 2:3, 드럼 정사각 확정. 추정으로 세웠던 letterbox 표가 그대로 확정됐고,
`DRUM_IMAGE_ASPECT_RATIO = 1`이 실제와 맞는다는 것도 확인됐다.

### 9-3. "드럼탭이 세로전용으로 보이기만 하면 문제는 안 생기는 거지?"

**아니다.** 세로 잠금이 없애는 건 829×393 한 케이스뿐이고, 나머지 5개 중 4개는 세로에서 생긴다.

지금 코드가 요구하는 건 방향이 아니라 **비율**이다 — `창높이 ≥ 1.787 × 창너비 + 76`.
**800×1280 태블릿이 세로인데도 버튼이 잘린다**는 것이 그 반증이다.

→ 세로 잠금은 "안 고쳐도 되게" 만드는 게 아니라 "경우의 수를 하나 잘라내는" 조치다.
사용자 판단으로 화면 방향은 건드리지 않기로 했다.

### 9-4. 틀렸다가 고친 것 ① — "320/360에서 드럼 10~13% 축소가 필요하다"

**철회했다.** 계산 실수가 아니라 **항목을 따로따로 계산한 탓**이다.

- 축소 추정은 항목 2(드럼 밀림)만 보고, `paddingBottom: 70`은 남긴다는 전제로 세운 값이었다.
- 그런데 항목 4(마커 어긋남)의 원인이 **바로 그 70**이다. 4를 고치려면 어차피 걷어내야 한다.
- 70을 걷으면 같은 세로 예산에서 그림이 커진다. 항목 2가 요구하던 축소를 항목 4의 수정이 상쇄한다.

| 320×568, 압축 켠 상태 | 상자 S | 실제 그림 | 현재(218) 대비 |
|---|---|---|---|
| 70 유지 (첫 추정) | 259 | 189 | −13% |
| 70 제거 (실제 채택) | — | 230 | **+5.7%** |

> **교훈** — 수정 항목이 같은 상수를 공유하면 따로 계산한 결론은 틀린다.
> 항목별 견적을 내기 전에 어느 상수를 공유하는지부터 본다.

### 9-5. 틀렸다가 고친 것 ② — "마커가 그림과 어긋나 있다"

**절반만 맞았다.** 계산상 어긋남(가로 ±24.5dp, 세로 최대 31.5dp)은 사실이다.
그런데 `drumLayouts.ts`의 좌표는 **70이 있는 상태에서 393dp 기기 화면을 보고 맞춘 값**이라,
그 어긋남을 이미 흡수하고 있었다.

`last_22.png`(540×540) 실측으로 확인한 근거:

| | 그림 실측 | 70 있을 때 마커가 가리키던 곳 | 70 없앴을 때 |
|---|---|---|---|
| snare | (0.34, 0.36) | (0.338, **0.312**) | (0.37, **0.25**) |
| kick | (0.62, 0.435) | (0.587, **0.436**) | (0.57, **0.35**) |

kick 세로가 0.436 대 0.435로 거의 정확했다. **70이 있는 쪽이 그림과 맞았다.**

→ 그래서 좌표를 "고치는" 게 아니라 **기계적으로 환산**했다. 눈으로 다시 맞추지 않았고,
393dp 화면은 ±0.3dp 안에서 그대로 재현된다.

> **교훈** — 계산상 어긋남을 발견해도, 그 값이 이미 특정 기기에서 눈으로 튜닝된 것이라면
> "틀린 값"이 아니라 "그 기기 전용 값"이다. 지우지 말고 환산한다.

### 9-6. 틀렸다가 고친 것 ③ — `paddingBottom: 70`만 지우면 공간이 회수된다는 오해

> **사용자** — (70을 직접 삭제하고) "삭제했는데 문제 없지?"

**문제 있었다.** `drumSetContainer`는 `height: drumSetSize`로 **높이가 명시**돼 있고
RN은 border-box라 70은 그 높이 **안**에 있었다.

| | 상자 높이 | 그려지는 그림 |
|---|---|---|
| 삭제 전 | S | S − 70 |
| 삭제 후 | **S (그대로)** | **S** |

즉 70 삭제는 공간 회수가 아니라 **그림을 70dp 키운 것**이었다. 세로 예산·버튼 잘림 계산은
하나도 안 변하고, 393dp에서 드럼만 25% 커지고 마커가 30~39dp 떠올랐다.

→ 「70 제거 + 크기식 `0.9W`→`0.72W` + 좌표 환산 + 캐릭터 계수 환산」이 **한 세트**여야 한다.
사용자가 B안(세트로 마무리)을 선택했다.

### 9-7. 사용자가 정한 것

| 70 처리 | **B안** — 삭제 유지 + 크기식·좌표·캐릭터 계수 함께 환산 |
