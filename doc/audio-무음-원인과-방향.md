## 2. 메커니즘 — 왜 이렇게 되나

### `createAudioPlayer` 하나가 잡는 것

`createAudioPlayer()` 한 번은 JS 객체 하나가 아닙니다.

```
createAudioPlayer(음원)
  └─ ExoPlayer 인스턴스           (expo-audio AudioPlayer.kt:36-56)
  └─ MediaSession 등록            (AudioPlayer.kt:67)
  └─ setMediaSource() → prepare() (AudioPlayer.kt:93-98)
       └─ MediaCodec 오디오 디코더
       └─ ★ AudioTrack ★          ← 시스템 전체에서 개수가 제한된 자원
  └─ 상태 갱신 코루틴 (500ms 주기, 영구)  (BaseAudioPlayer.kt:52-69)
```

### 자원을 잡는 시점이 "재생"이 아니라 "생성"

이게 가장 반직관적인 부분입니다.

`prepare()`는 재생 여부와 무관하게 렌더러를 켜고 버퍼를 채웁니다.
그 과정에서 `DefaultAudioSink`가 **AudioTrack을 미리 할당합니다.**

> **만들어만 두고 한 번도 안 울린 플레이어도 자리를 차지하고 있습니다.**

logcat이 이걸 증명합니다 — 터치 11초 전, 프리로드 시점에 에러가 났습니다.

### 한도

AOSP `AudioFlinger`의 UID당 트랙 상한은 **40개** 수준입니다 (기기·OS별로 다를 수 있음).
넘으면 `createTrack_l()`이 `-12`로 실패하고, ExoPlayer는 그 플레이어를 에러 상태로 떨굽니다.

## 3. 간과한 것 — 7가지

이번 문제의 핵심입니다. 하나하나가 독립적인 판단 착오였습니다.

### ① 플레이어를 "메모리 문제"로만 봤다

세션 6~7에서 프리로드를 결정할 때 검토한 축은 **메모리(파일 크기)** 였습니다.
"기타 28 + 피아노 52 + 드럼 5 = 85개가 남는다, 사용자는 메모리 문제 없다고 판단" (`handoff.md:909-911`).

메모리는 실제로 문제가 아니었습니다. **문제는 메모리가 아니라 개수였습니다.**
음원 파일이 아무리 작아도 AudioTrack은 파일 크기와 무관하게 1개씩 소모됩니다.

> 봐야 했던 축: **동시 개수 한도**

### ② 예산이 "화면별"이 아니라 "앱 전체"라는 걸 놓쳤다

피아노 52개를 정할 때 피아노 화면만 봤습니다.
그런데 **탭은 언마운트되지 않고, 캐시도 비우지 않기로 했으므로** 모든 탭의 플레이어가 동시에 살아 있습니다.

logcat에서 피아노 때문에 **단어 탭 "탈"이 무음**이 된 게 그 결과입니다.
서로 다른 화면이 같은 예산을 갉아먹는 구조인데, 화면 단위로만 설계했습니다.

### ③ 상한값(15)을 "근거 없음"과 "불필요"로 혼동했다

`CACHE_LIMIT = 15`를 지울 때의 기록:

> "**기타 `CACHE_LIMIT = 15`는 실측값이 아니다.**" → 세션 7에서 삭제 (`handoff.md:902`)
> "왜 이전에 안 했나: 의도는 있었습니다. **음이 많아서 LRU 15로 제한**한 것이고,
> 파일 크기·기기 한도를 재고 고른 숫자는 문서에 없습니다." (`handoff.md:1157`)

**"기기 한도를 재고 고른 숫자가 아니다"는 관찰은 정확했습니다.**
거기서 내린 결론이 틀렸습니다. "숫자에 근거가 없다 → 한도 자체가 없다"로 넘어갔습니다.

실제로는 **한도는 실재했고, 15가 우연히 그 아래였을 뿐**입니다.
근거 없는 숫자를 만났을 때 할 일은 삭제가 아니라 **측정**이었습니다.

### ④ 오디오 에러가 JS에 안 보이는 구조를 몰랐다

expo-audio는 재생 에러를 **이벤트로만** 보냅니다.

```kotlin
// expo-audio/android/.../AudioPlayer.kt:158
override fun onPlayerError(error: PlaybackException) {
  sendStatusUpdate(mapOf("error" to error.message))   // playbackStatusUpdate 이벤트
}
```

- 어느 화면도 이 이벤트를 **구독하지 않습니다**
- `play()`는 `Function`이라 **예외를 던지지 않습니다** (`AudioModule.kt:467`)
- `seekTo()`도 실패하지 않습니다

결과: `playSound`의 `try/catch`는 **절대 안 걸립니다.**

> **에러 없이, 로그 없이, 조용히 무음.**
> 세션 15에서 "재생 실패 로그는 없다"를 "재생은 성공했다"로 읽은 근거가 이겁니다.

### ⑤ 최적화 대상을 "지연" 하나로 잡았다

세션 6~8의 모든 결정이 **첫 소리 지연**을 향해 있었습니다. 프리로드, 캐시 비우지 않기, LRU 삭제 전부 같은 방향입니다.

지연은 실제 문제였고 개선도 됐습니다. 하지만 **한 축만 밀면 다른 축이 무너집니다.**
용량(개수)이라는 축을 아무도 안 봤습니다.

### ⑥ 실기기 로그를 안 봤다

세션 15에서 세 번 오진했습니다. 전부 **코드만 읽고 추론**한 결과입니다.

| 회차 | 진단 | 실제 |
|---|---|---|
| 1 | `currentTime > 0`일 때만 `seekTo` → pause 후 무음 | ❌ 무관 |
| 2 | 첫 진입 시 로드 미완료 | ❌ 무관 |
| 3 | 블러가 미로드 플레이어까지 `pause()` | ❌ 무관 |

`adb logcat` 한 번으로 3분 만에 확정됐습니다.
**네이티브 자원 문제는 JS 코드를 아무리 읽어도 안 보입니다.**

### ⑦ "탭은 언마운트되지 않는다"의 대가를 절반만 계산했다

이 사실 자체는 정확히 파악하고 문서화까지 했습니다 (`useStopAudioOnBlur.ts:7-9`).
그래서 "블러 때 정지"라는 대응까지 나왔습니다.

하지만 **정지는 소리만 멈추지 자원은 안 돌려줍니다.**
"언마운트 안 됨 → 소리가 계속 남" 은 봤는데, "언마운트 안 됨 → **자원이 계속 쌓임**" 은 못 봤습니다.

## 6. 방향 1 — 개수 제한 (LRU 복원)

> **스피커를 다 사놓지 않고, 최근에 친 음 N개만 들고 있는다.**

### 어떻게 동작하나

```
건반 누름
  ├─ 캐시에 있음  → 즉시 재생 (지연 0)
  └─ 캐시에 없음  → 가장 오래 안 쓴 것 하나 버리고
                    새로 만들어 재생 (지연 있음)
```

### 바뀌는 코드

| 파일 | 변경 |
|---|---|
| `MusicTrainingScreen.tsx:582-593` | 전체 프리로드 삭제 |
| `MusicTrainingScreen.tsx:673-688` | `CACHE_LIMIT` + `recentlyUsedNotes` 복원 |
| `guitar/_layout.tsx:106-117` | 동일 |
| `useStopAudioOnBlur` 콜백 | `pause()` → `remove()` + 캐시 비움 |

`b48fec8`을 되돌리는 수준이라 **작업량이 가장 작습니다.**

### 장점

- 되돌리기 수준. 구조를 안 바꿈
- 한 번 친 음은 그 방문 동안 **지연 0**
- 폴리포니(동시에 여러 음) 그대로 유지

### 단점

**1) N을 크게 못 잡습니다 (핵심 문제)**

3·4단계 화면에는 **백건 16 + 흑건 약 11 = 27건반**이 보입니다 (`MusicTrainingScreen.tsx:417`).
"화면에 보이는 건 다 담자"면 N = 27이어야 합니다.

그런데 4장에서 계산한 실제 예산은 **약 14**입니다.

> **화면에 보이는 건반의 절반밖에 못 담습니다.**
> 한 옥타브만 훑어도 앞 음이 쫓겨나고, 다시 누르면 또 지연됩니다.
>
> 예전 `CACHE_LIMIT = 15`가 정확히 이 상태였습니다.
> **없앤 이유였던 "연주 중 지연"이 그대로 돌아옵니다.**

**2) 탭 재진입 첫 음 지연**

캐시를 비워야 하므로 돌아올 때마다 다시 만듭니다.
"캐시는 블러 때 비우지 않는다"는 세션 7의 규칙을 **깨야 합니다.**

**3) 배경 상주분에 취약**

동물게임 12개는 앱 종료까지 안 사라집니다.
동물게임을 한 번이라도 켜면 피아노 예산이 12개 줄어듭니다.
**다른 탭을 어떤 순서로 다녀왔느냐에 따라 피아노가 되기도 안 되기도 합니다.**

### 평가

되돌리기는 쉽지만, **없앴던 문제를 그대로 되살립니다.**
N을 27로 키우면 지연은 해결되지만 한도를 다시 넘습니다. **N 하나로 두 조건을 동시에 만족시킬 수 없습니다.**

## 7. 방향 2 — 플레이어 재사용 (고정 풀 + `replace()`)

> **스피커를 12개만 사두고, 건반을 칠 때마다 그 스피커에 음원을 갈아 끼운다.**

### 어떻게 동작하나

핵심은 **"플레이어 = 음"이라는 1:1 대응을 끊는 것**입니다.

```
[스피커 풀 — 12개 고정, 앱 내내 이 12개가 전부]

건반 C4 누름
  → 지금 안 울리는 스피커 하나 고름 (라운드로빈)
  → player.replace(C4 음원)      ← 음원만 교체, 플레이어는 그대로
  → player.play()

건반 E4 누름 (C4 울리는 중)
  → 다음 스피커 고름
  → replace(E4) → play()          ← 동시에 남 (폴리포니 유지)
```

expo-audio가 `replace()`를 제공합니다 (`AudioModule.kt:488-506`).
**플레이어를 만들지도 버리지도 않으므로 AudioTrack 개수가 12에서 절대 안 움직입니다.**

### 바뀌는 코드

| 파일 | 변경 |
|---|---|
| 새 파일 (예: `services/NotePlayerPool.ts`) | 풀 구현 |
| `MusicTrainingScreen.tsx` | `soundCache` 전부 삭제 → 풀 호출로 교체 |
| `guitar/_layout.tsx` | 동일 |
| `useStopAudioOnBlur` | 풀 정지만. 비울 필요 없음 |

피아노·기타가 **같은 풀을 공유**할 수 있습니다. 그러면 두 탭 합쳐서도 12개입니다.

### 장점

- **개수가 상수.** 탭을 얼마나 오래 쓰든, 몇 번 오가든 12개
- **캐시를 비울 필요가 없음** → 세션 7의 "비우지 않는다" 규칙을 유지
- **다른 탭 순서에 영향받지 않음** — 예산 계산이 필요 없어짐
- 음이 52개든 100개든 **음원 개수와 무관**
- 배경 상주 26 + 12 = 38 < 40 ✅

### 단점

**1) 매번 약간의 지연**

`replace()`는 새 음원을 `prepare()` 합니다. 로컬 파일이라 짧지만 0은 아닙니다.

> 방향 1: 대부분 지연 0, **가끔 크게** 걸림
> 방향 2: **항상 조금씩** 걸림

체감이 다릅니다. 방향 2가 더 고르고, 방향 1이 최고점은 더 좋습니다.

**2) 동시 발음이 12개로 제한**

건반 12개를 동시에 누를 일은 없으니 실질 제약은 아닙니다.
다만 피아노는 음이 길어서(감쇠 3초 이상) **빠르게 연타하면 아직 울리는 스피커를 재활용**하게 됩니다.
→ 앞 음이 끊깁니다. 12개면 3초 안에 12타를 쳐야 발생하므로 현실적으로 드뭅니다.

**3) 작업량이 큽니다**

`soundCache` 구조를 걷어내고 풀을 새로 짭니다. 피아노·기타 양쪽 + 낙하노트 모드까지 확인 필요.

**4) `replace()` 동작 확인이 필요합니다**

`replace()`는 `COMMAND_CHANGE_MEDIA_ITEMS` 가능할 때만 동작하고, 재생 중이면 이어서 재생합니다
(`AudioModule.kt:488-506`). **연타 시 의도대로 되는지 실기기 확인이 필요합니다.**

### 평가

**구조적으로 옳은 해법입니다.** 게임 오디오 엔진이 쓰는 표준 방식(보이스 풀)이고,
"음원 개수"와 "동시 재생 개수"를 분리합니다.

---

## 8. 방향 3 — 둘의 실제 중간

> **풀 12개를 두되, 각 스피커가 마지막에 물었던 음을 기억한다.**

```
건반 누름
  ├─ 그 음을 이미 물고 있는 스피커 있음 → replace 없이 seekTo(0) + play()   ← 지연 0
  └─ 없음 → 가장 오래된 스피커에 replace()                                  ← 지연 있음
```

방향 2의 풀 위에 방향 1의 LRU를 얹은 것입니다.

- 최근 12음은 **지연 0** (방향 1의 장점)
- 개수는 **12 고정** (방향 2의 장점)
- 작업량은 방향 2와 비슷

**두 방향의 장점을 실제로 다 가집니다.** 방향 2를 하기로 했다면 사실상 추가 비용 없이 여기까지 갈 수 있습니다.

## 9. 비교

| | 방향 1 (LRU) | 방향 2 (풀+replace) | 방향 3 (중간) |
|---|---|---|---|
| 동시 플레이어 | N개 (≈14 이하여야) | **12 고정** | **12 고정** |

# 13. 실행 결과 — 계획대로 한 뒤에 드러난 것

추가: 2026-08-16 (세션 16)
전제: **방향 1**(LRU 12 + 블러 시 `remove()`)이 이미 적용된 상태
검증: 실기기 · USB 연결 · 개발 빌드

여기까지(1~12장)는 **계획서**였습니다. 계획대로 하고 나서 **계획에 없던 문제**가 하나 나왔습니다.
그 문제를 찾게 해준 것도, 그 문제가 생기게 한 것도, 전부 **10장 ①**에서 갈라집니다.

---

## 13-1. 10장 ①이 실제로 첫 열쇠였다

10장 ①에 "어느 방향이든 같이 해야 할 것"으로 이렇게 적어뒀습니다.

```ts
player.addListener('playbackStatusUpdate', (status) => {
  if (status.error) console.warn(`[audio] ${note} 재생 에러:`, status.error);
});
```

> **이것만 있었으면 첫 턴에 끝났습니다.** (10장 ①)

실제로 달았습니다. 그리고 터미널에 **처음으로** 이런 줄이 떴습니다.

```
WARN  [audio] 'F#2' 재생 에러: Source error
WARN  [audio] 'G#2' 재생 에러: Source error
```

피아노 5단계(검은건반) 훈련 뒤 3·2단계로 넘어가는 구간에서 나왔습니다.
**이 두 줄이 세션 16의 출발점 전부입니다.** 리스너가 없었다면 이 세션은 시작조차 안 됐습니다.

> 예측이 맞았습니다. 다만 맞은 방식이 예상과 달랐습니다 —
> 이 리스너는 **1장의 무음을 잡으려고** 넣은 것인데, **전혀 다른 실패**를 잡았습니다.

---

## 13-2. `Source error`는 1장의 한도 문제가 아니다

같은 "무음"이라도 층이 다릅니다. 이걸 섞으면 진단이 어긋납니다.

`Source error`는 ExoPlayer `PlaybackException`의 메시지이고, `AudioPlayer.kt:158`이 그대로 JS로 넘긴 값입니다.
**TYPE_SOURCE** — 음원을 **여는/읽는** 단계에서 실패했다는 뜻입니다.

| | 1장의 무음 | 이번 무음 |
|---|---|---|
| 층 | **출력** (AudioTrack 할당) | **입력** (미디어 소스 로드) |
| 원인 | 앱 전체 트랙 개수 한도 초과 | 음원을 못 열거나 못 읽음 |
| logcat | `no more tracks available` / `Cannot create AudioTrack` | `ExoPlaybackException` (TYPE_SOURCE) |
| 범위 | 한도를 넘긴 **모든** 플레이어 | **그 음 하나** |
| 대책 | 개수 줄이기 (방향 1·2·3) | — |

개발 빌드에서는 `require()`한 음원이 Metro 개발 서버에서 **HTTP로** 로드됩니다.
그래서 개발 서버 쪽 문제일 가능성이 큽니다 (릴리스 빌드는 에셋이 앱에 번들됨).
**다만 이건 추론이고, 원인은 이 세션에서 확정하지 못했습니다.**

---

## 13-3. 계획에 없던 문제 — 리스너가 "알리기만" 했다

여기가 이 장의 핵심입니다.

10장 ①은 **진단 장치**였습니다. 에러가 났다고 알려줍니다. 그게 전부입니다.
`console.warn`은 터미널에 글자를 찍을 뿐, **캐시에는 아무 영향이 없습니다.**

```
F#2 터치 (1회)
  → 캐시에 없음 → createAudioPlayer → 소스 로드 실패
  → soundCache['F#2'] = 죽은 플레이어      ← 자리를 차지한 채 남는다
  → console.warn(...)                       ← 알리기만
  → 무음

F#2 터치 (2회)
  → 캐시에 있음! → 그 죽은 플레이어를 그대로 재사용
  → 무음                                     ← 에러 로그조차 다시 안 뜬다
```

**죽은 플레이어가 "그 음의 플레이어" 자리를 계속 지킵니다.**
탈출구는 두 개뿐이었습니다 — 탭을 나갔다 오거나(`useStopAudioOnBlur`가 전부 `remove()`),
LRU 12칸에서 밀려나거나. **둘 다 운에 맡겨져 있었습니다.**

사용자가 "지금은 다시 잘 된다"고 한 것도 이것으로 설명됩니다. 고쳐진 게 아니라,
그 사이 탭을 옮겼거나 다른 음 12개가 밀어낸 것입니다.

---

## 13-4. 왜 "충분히 잘 된다"고 믿었나 — 최적화가 실패의 수명을 늘렸다

세션 6~15 동안 재생은 계속 다듬어졌습니다. 하나하나가 실제 개선이었습니다.

| 개선 | 목적 |
|---|---|
| 탭 진입 시 프리로드 | 첫 음 지연 0 |
| 탭을 나가도 캐시 유지 | 재진입 지연 0 |
| `await seekTo(0)` 후 `play()` | 되감기 경합 제거 |
| LRU + `CACHE_LIMIT` | 개수 한도 준수 (1장) |
| 백업 타이머 (단어) | 완료 신호 누락 대비 |

**다섯 개 전부 "성공 경로"를 다듬은 것입니다.** 재는 자도 하나였습니다 —
*얼마나 빨리, 얼마나 안 끊기고 나는가.* 그 축에서는 실제로 잘 다듬어져 있었습니다.

문제는 **실패 경로는 한 번도 손대지 않았다**는 것입니다.
그리고 오디오 실패는 조용합니다 (3장 ④) — 예외도 없고 로그도 없습니다.

> "잘 된다"의 근거는 **"이상 신호가 없다"** 였는데,
> 실제로는 **이상 신호를 받는 배선이 없었습니다.**
> 무소식이 희소식이 아니라, 소식통이 없었던 겁니다.

여기까지는 3장 ④에 이미 적힌 이야기입니다. **이번에 새로 드러난 건 그다음입니다.**

### 캐시는 성공만 골라 기억하지 않는다

캐시는 **성공을 재사용하려고** 만든 장치입니다. 그런데 캐시에게 성공과 실패는 구분이 없습니다.
한 번 죽은 플레이어도 똑같이 "그 음의 플레이어"로 자리를 지킵니다.

```
캐시 없음  →  매번 새로 만듦  →  실패해도 다음 재생은 새 플레이어  →  저절로 회복
캐시 있음  →  한 번 만든 걸 계속 씀  →  실패한 것도 계속 씀      →  영구 무음
```

즉 **"오래 살려두기"라는 최적화가, 고장난 것까지 오래 살려뒀습니다.**
그래서 **최적화가 공격적인 곳일수록 무음이 오래갔습니다.**

| 화면 | 캐시 최적화 강도 | 죽은 플레이어의 수명 |
|---|---|---|
| 🎹 피아노 · 🎸 기타 | 캐시 유지, 단 탭 이탈 시 `remove()` | 탭 나갔다 오면 회복 |
| 🎧📖 단어 | **탭 이탈에도 캐시 유지** (가장 공격적) | **앱 재시작까지** |

**가장 잘 최적화된 단어 탭이, 가장 오래 죽어 있는 구조였습니다.**

> 성능 최적화는 **성공을 짧게** 만들고 **실패를 길게** 만듭니다.
> 빠른 길을 깔았다면, 그 길 위에 선 고장난 차를 치우는 장치도 같이 깔아야 합니다.

### 그래서 마지막 한 칸은 속도가 아니라 자기 회복이었다

성능 축은 이미 짤 만큼 짜여 있었습니다. 3줄을 더 써서 줄일 수 있는 건 몇 ms입니다.
**반면 신뢰성 축은 0에서 시작이었습니다.** 같은 3줄을 회복에 쓰면
**"앱 재시작까지 영구 무음"이 "한 번 더 누르면 소리 남"으로** 바뀝니다.

이게 이번 수정이 최적화로서 값어치가 있었던 이유입니다.
빠르게 만든 게 아니라, **빠르게 만들면서 생긴 부채를 갚은 것**입니다.

---

## 13-5. 수정 — 에러 나면 캐시에서 축출한다

원리는 한 줄입니다. **진단 장치를 치료 장치로 바꿉니다.**

```
에러 이벤트 도착
  → 로그 (기존)
  → 캐시에서 그 항목 제거   ← 추가
  → player.remove()          ← 추가 (AudioTrack 반납)
  → 다음 터치는 캐시 미스 → 새 플레이어 → 회복
```

| 파일 | 위치 | 내용 |
|---|---|---|
| `screens/MusicTrainingScreen.tsx` | `playSound` (`:709-729`) | `soundCache` · `recentlyUsedNotes`에서 제거 후 `remove()` |
| `app/(tabs)/guitar/_layout.tsx` | `playSound` (`:178-198`) | 동일 |
| `hooks/useWordAudioPlayer.ts` | `playWordSound` (`:170-189`) | `playerCache`에서 제거. **해제 전에 구독·`currentPlayerRef` 먼저 끊음** |

### 신원 확인이 필요한 이유

에러 이벤트는 **늦게 도착합니다.** 그사이 그 자리가 이미 LRU로 축출됐거나 다른 플레이어로 교체됐을 수 있습니다.
그대로 지우면 **멀쩡한 남의 플레이어를 지웁니다.**

```ts
if (soundCache.current[note] !== createdPlayer) return;   // 내가 만든 그 플레이어일 때만
```

그래서 생성 시점의 플레이어를 `createdPlayer`로 붙잡아 두고, 지우기 직전에 신원을 확인합니다.

### 단어만 한 가지 더

단어는 리스너를 **재생마다** 새로 걸고 `stopCurrentPlayback()`이 나중에 `player.pause()`를 부릅니다.
참조를 남긴 채 `remove()`하면 **이미 해제된 플레이어를 pause하게 됩니다.**
그래서 해제 전에 `subscriptionRef` · `currentPlayerRef`를 먼저 끊습니다.
(피아노·기타는 리스너가 플레이어에 붙박이라 이 문제가 없습니다.)

자세한 것은 → **`doc/단어탭-재생에러-회복.md`**

## 13-6. 검증 — 실패를 일부러 만들어서 확인했다

재현을 기다릴 수 없어서 **실패를 주문 제작**했습니다.

처음엔 Wi-Fi를 끊어 Metro 연결을 끊는 방법을 쓰려 했는데, **USB 연결이라 못 씁니다** —
`adb reverse`로 USB 터널을 타므로 Wi-Fi를 꺼도 개발 서버에 그대로 붙습니다.

그래서 임시 코드로 특정 음 하나만 **첫 생성 때** 깨진 주소를 물렸습니다.

```ts
// ⚠️ 임시 — 검증 후 삭제함
const forceBroken = note === TEST_NOTE && !TEST_BROKEN_DONE;
if (forceBroken) TEST_BROKEN_DONE = true;
player = createAudioPlayer(forceBroken ? { uri: 'http://127.0.0.1:1/broken.m4a' } : soundFiles[note]);
```

캐시 키는 원래 소스 그대로이므로, 축출이 동작하면 **두 번째는 진짜 파일로** 새로 만들어집니다.

| 대상 | 1차 터치 | 2차 터치 | 결과 |
|---|---|---|---|
| 🎹 피아노 `C#2` | 무음 + `Source error` 로그 | **소리 남** | ✅ |
| 🎧 단어 (첫 재생 단어) | 무음 + `Source error` 로그 | **소리 남** | ✅ |
| 🎸 기타 | — | — | 미실측 (코드는 피아노와 동일) |

**판정 기준을 로그가 아니라 "2차에서 소리가 나는가"로 잡은 것이 중요합니다.**
수정 전이라면 2차도 무음이어야 했습니다. 소리가 났다는 건 **다른 플레이어가 만들어졌다**는 뜻이고,
그건 죽은 것이 캐시에서 빠졌다는 직접 증거입니다.

임시 코드는 검증 후 전부 제거했습니다 (`git grep`으로 흔적 없음 확인).

## 13-7. 이번에 얻은 원칙

1. **진단과 치료는 다르다.** 10장 ①은 진단까지였다. 알림만으로는 아무것도 안 낫는다.
2. **캐시를 넣으면 무효화 규칙도 같이 넣는다.** 캐시는 성공과 실패를 구분하지 않는다.
3. **최적화가 강한 곳일수록 실패가 오래 산다.** 오래 살려두는 설계는 고장도 오래 살린다.
4. **"에러가 안 보인다"와 "에러가 없다"는 다르다.** 배선을 깔기 전의 침묵은 정보가 아니다.
5. **재현을 기다리지 말고 만든다.** 깨진 주소 한 줄이면 실패 경로를 언제든 켤 수 있다.

## 13-8. 이 시점의 상태와 남은 것

**끝난 것**

- 재생 에러 후 **자동 회복** — 피아노 · 기타 · 단어 세 곳
- 피아노 · 단어는 실기기에서 회복 확인

**안 한 것 / 모르는 것**

- **`Source error`의 근본 원인** — 미해결. 개발 서버 HTTP 로드 실패로 **추정**만 함.
  다음 단서는 **릴리스 빌드에서도 이 경고가 뜨는지** 여부. (사용자 판단으로 이번엔 보류)
- **기타 탭 실측** — 코드는 피아노와 동일하나 직접 눌러보진 않음
- **단어의 첫 실패 3초** — 실패해도 백업 타이머가 3초를 기다린 뒤 넘어감.
  0으로 만들 수 있으나 이번엔 보류 (→ `doc/단어탭-재생에러-회복.md`)
- **드럼 탭** — 같은 문제가 있는지 확인 안 함
- 7·8장의 **방향 2·3**(풀 + `replace()`)은 여전히 미착수. 이번 수정과 무관하게 유효함

**10장의 나머지 항목**

- ① 재생 에러를 JS에서 볼 수 있게 하기 → ✅ **완료**, 그리고 이 장이 그 후속
- ② 동물게임 12개 떼어내기 → 미착수
- ③ `[Touch debug]` 로그 정리 → 미착수 (아직 남아 있음)
- ④ `adb logcat` 확인법 기록 → ✅ 10장 ④에 기록됨

> 참고: 10장 ④의 `adb logcat` 명령은 **1장의 출력 층 무음**을 잡는 것입니다.
> 이번 `Source error`는 입력 층이라 그 명령에 안 걸립니다 (13-2). 층에 따라 도구가 다릅니다.
