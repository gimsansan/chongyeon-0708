# 단어 탭 — 재생 에러 자동 회복

작성: 2026-08-16 (세션 16)
대상: 🎧 learn(`WordGame`) · 📖 flashcards(`WordFlashcard`)가 함께 쓰는 `hooks/useWordAudioPlayer.ts`
관련: `doc/audio-무음-원인과-방향.md` 13장 (피아노·기타의 같은 수정)
검증: 실기기 · USB 연결 · 개발 빌드 — **회복 확인 완료**

---

## 0. 한 줄 요약

**단어 하나가 재생에 실패하면, 그 단어는 앱을 껐다 켤 때까지 무음이었습니다.**

단어 캐시는 탭을 나가도 안 비워지도록 최적화돼 있습니다. 그 최적화가
**죽은 플레이어까지 붙잡아두는 부작용**을 낳았습니다. 이제 실패한 플레이어는 즉시 캐시에서 빠지고,
**한 번 더 누르면 소리가 납니다.**

---

## 1. 왜 단어 탭을 따로 봐야 했나

피아노·기타를 고치고 나서 같은 문제가 다른 곳에도 있는지 훑다가 나왔습니다.
같은 뿌리인데 **증상이 달랐습니다.** 세 가지가 다릅니다.

| | 🎹 피아노 · 🎸 기타 | 🎧📖 단어 |
|---|---|---|
| 캐시 위치 | 컴포넌트 `useRef` | **모듈 단위 `Map`** (`useWordAudioPlayer.ts:31`) |
| 탭 이탈 시 | `useStopAudioOnBlur`가 전부 `remove()` | **아무것도 안 함 — 의도된 설계** |
| 에러 감지 | `status.error` 로그 있었음 | **`status.error`를 아예 안 봄** |
| 리스너 수명 | 플레이어에 붙박이 (1회 등록) | **재생마다 새로 걸고 뗌** |

이 차이가 **더 나쁜 증상**과 **더 조심해야 할 수정**을 동시에 만들었습니다.

---

## 2. 문제 — 세 겹으로 겹쳐 있었다

### 겹 1. 에러가 로그조차 안 남았다

`playWordSound`의 리스너는 두 가지만 읽고 있었습니다.

```ts
// 수정 전 (:157~)
player.addListener('playbackStatusUpdate', (status) => {
  if (status.duration > 0) { /* 진행도 갱신 + 백업 타이머 재무장 */ }
  if (status.didJustFinish) { /* 완료 처리 */ }
});
```

`status.error`는 읽지 않았습니다. expo-audio는 재생 에러를 **이 이벤트로만** 보냅니다
(`AudioPlayer.kt:158`). `play()`는 예외를 던지지 않고, `try/catch`도 안 걸립니다.

> **에러 없이, 로그 없이, 조용히 무음.**
> 피아노는 최소한 경고라도 떴는데, 단어는 그것조차 없었습니다.

### 겹 2. 죽은 플레이어가 캐시에 남았다

```ts
function getPlayer(source) {
  const cached = playerCache.get(source);
  if (cached) return cached;          // ← 죽었어도 그대로 돌려준다
  ...
}
```

`playerCache`는 **소스 → 플레이어** 대응표입니다. 한 번 실패한 플레이어도
"그 단어의 플레이어" 자리를 그대로 지킵니다. 다음 재생도 같은 것을 씁니다.

### 겹 3. 탈출구가 거의 없었다

피아노는 탭을 나갔다 오면 `useStopAudioOnBlur`가 캐시를 통째로 비웁니다. **단어에는 그게 없습니다.**
그리고 그건 실수가 아니라 **명시된 의도**입니다.

```ts
/**
 * 훅 바깥(모듈 단위)에 두어 화면을 나갔다 들어와도, 두 탭을 오가도 캐시가 유지됩니다.
 */
const playerCache = new Map<any, AudioPlayer>();   // :26-31
```

그래서 회복 조건이 이 둘뿐이었습니다.

```
① 다른 단어 8개가 재생돼서 LRU로 밀어내기   (CACHE_LIMIT = 8)
② 앱 재시작
```

플래시카드처럼 **같은 단어 몇 개만 반복**하는 상황이면 ①도 안 옵니다.
**그 단어는 앱을 껐다 켤 때까지 죽어 있습니다.**

### 겹치면

```
단어 A 재생  →  로드 실패  →  로그 없음  →  캐시에 죽은 채로 저장
단어 A 재생  →  캐시 히트  →  죽은 것 그대로 사용  →  무음
단어 A 재생  →  ... (앱 재시작까지 반복)
```

**아무도 모르게, 아무 흔적 없이, 그 단어만 계속 안 들립니다.**
듣기 훈련 앱에서 이건 아이가 못 맞히는 것으로 기록됩니다.

## 3. 그나마 나았던 점 — 흐름은 안 멈춘다

`playWordSound`는 `play()` 직후 **백업 타이머**를 무조건 겁니다.

```ts
// :216-218
armBackupTimer(
  player.duration > 0 ? player.duration * 1000 + BACKUP_GRACE_MS : BACKUP_FALLBACK_MS
);
```

원래는 "완료 신호가 안 올 때를 대비한" 장치인데, 실패한 플레이어에도 그대로 작동합니다.
실패하면 `duration`이 **0**이라 `BACKUP_FALLBACK_MS = 3000`으로 잡히고,
3초 뒤 타이머가 `onComplete`를 불러 **훈련 흐름은 다음으로 넘어갑니다.**

> 멈추진 않습니다. 대신 **3초 동안 "재생 중..."이라고 표시된 채 아무 소리도 안 납니다.**
> (`WordGame.tsx:294`가 `isPlaying`으로 그 문구를 띄웁니다. 진행도 파형도 0에 멈춰 있다가 1로 튑니다.)

플래시카드 "전체 듣기"는 word1 완료 → 300ms → word2로 이어지므로(`WordFlashcard.tsx:86-92`),
두 단어가 다 실패하면 **3 + 0.3 + 3 = 6.3초**를 "재생 중" 표시로 서 있다가 끝납니다.

## 4. 해결 원리

한 줄입니다.

> **에러를 알리는 데서 끝내지 않고, 그 자리에서 캐시를 무효화한다.**

```
에러 이벤트 도착
  ├─ 로그를 찍는다                    ← 진단 (다음에 또 나면 알 수 있게)
  ├─ 구독·현재 플레이어 참조를 끊는다   ← 안전 (해제된 객체를 나중에 안 만지게)
  └─ playerCache에서 지우고 remove()   ← 치료
        ↓
  다음 재생 → getPlayer가 캐시 미스 → 새 플레이어 생성 → 소리 남
```

**핵심은 "캐시 미스를 일부러 만든다"는 것입니다.** 캐시는 성공을 재사용하려고 만든 장치인데,
성공과 실패를 구분하지 않습니다. 구분해주는 코드가 없으면 실패도 똑같이 재사용됩니다.

## 5. 코드 변화

### 5-1. 들어간 곳

`hooks/useWordAudioPlayer.ts` `playWordSound` 안의 리스너 (`:157` 등록, 에러 분기 `:170-189`), 한 군데뿐입니다.

```ts
subscriptionRef.current = player.addListener('playbackStatusUpdate', (status) => {
  if (currentPlaybackId !== playbackIdRef.current) return;

  // ▼▼▼ 추가된 부분 ▼▼▼
  if (status.error) {
    console.warn(`[audio] 단어 '${wordText}' 재생 에러:`, status.error);

    // 해제 전에 구독·참조부터 끊는다. 남겨두면 나중에 해제된 플레이어를 pause하게 된다
    subscriptionRef.current?.remove();
    subscriptionRef.current = null;
    if (currentPlayerRef.current === player) currentPlayerRef.current = null;

    // 그 사이에 축출·교체됐다면 남의 플레이어다. 건드리지 않는다
    if (playerCache.get(soundSource) === player) {
      playerCache.delete(soundSource);
      try {
        player.remove();
      } catch (removeError) {
        console.warn('단어 플레이어 해제 실패:', removeError);
      }
    }
    return;
  }
  // ▲▲▲ 여기까지 ▲▲▲

  if (status.duration > 0) { ... }
  if (status.didJustFinish) { ... }
});
```

`getPlayer` · `playerCache` · 백업 타이머 · 완료 처리는 **한 줄도 안 바꿨습니다.**

### 5-2. 네 줄이 각각 왜 필요한가

**① `console.warn`**
지금까지 단어 탭은 실패해도 흔적이 없었습니다. 다음에 또 나면 **최소한 알 수는 있게** 합니다.
단어 이름(`wordText`)을 같이 찍어서 어느 단어인지 바로 보입니다.

**② `subscriptionRef.current?.remove()` + `null`**
이 리스너는 **재생마다 새로 거는 구독**입니다. 아래에서 플레이어를 해제하면 이 구독은
**해제된 객체에 붙은 껍데기**가 됩니다. 다음 재생 때 `stopCurrentPlayback()`이
`subscriptionRef.current?.remove()`를 부르는데, 거기엔 `try/catch`가 없습니다(`:89`).
**미리 끊어두는 게 안전합니다.**

**③ `currentPlayerRef.current = null`**
같은 이유입니다. `stopCurrentPlayback()`은 이 참조로 `player.pause()`를 부릅니다(`:97`).
해제된 플레이어를 pause하면 무슨 일이 날지 보장이 없습니다.
`null`로 두면 `if (!player) return;`에서 조용히 빠져나갑니다.

> **이 두 줄은 피아노·기타에는 없습니다.** 거기는 리스너가 플레이어에 붙박이라
> 나중에 그 플레이어를 다시 만질 코드가 없습니다. **단어만의 추가 처리입니다.**

**④ `playerCache.get(soundSource) === player` 신원 확인**
에러 이벤트는 **늦게 도착할 수 있습니다.** 그사이 LRU가 이 항목을 축출하고
다른 플레이어가 그 자리에 들어갔을 수 있습니다. 확인 없이 지우면
**멀쩡한 남의 플레이어를 지웁니다.** 내가 만든 그 플레이어일 때만 지웁니다.

### 5-3. 일부러 안 건드린 것

**백업 타이머를 그대로 뒀습니다.** 에러 분기에서 `return`할 뿐 타이머는 손대지 않습니다.
그래서 3초 뒤 타이머가 평소처럼 `onComplete`를 부르고 흐름이 넘어갑니다.
**완료 처리 경로를 하나로 유지**하기 위해서입니다.

## 6. 검증 — 실패를 주문 제작했다

실제 `Source error`는 드물게 나서 기다릴 수 없었습니다. **일부러 만들었습니다.**

원래는 Wi-Fi를 끊어 Metro 연결을 끊으려 했는데 **USB 연결이라 안 됩니다** —
`adb reverse`로 USB 터널을 타므로 Wi-Fi를 꺼도 개발 서버에 그대로 붙습니다.
그래서 임시 코드를 썼습니다.

```ts
// ⚠️ 임시 — 검증 후 삭제함. 리로드 후 "처음 만드는 단어 하나"만 깨진 주소로
const forceBroken = !TEST_BROKEN_DONE;
if (forceBroken) TEST_BROKEN_DONE = true;
const player = createAudioPlayer(
  forceBroken ? { uri: 'http://127.0.0.1:1/broken.m4a' } : source,
  { updateInterval: UPDATE_INTERVAL_MS }
);
```

**캐시 키는 원래 `source` 그대로** 둔 것이 요령입니다. 그래야 축출이 동작했을 때
두 번째 재생이 **진짜 파일로** 새로 만들어집니다.

### 절차와 결과

| 단계 | 관측 |
|---|---|
| 1. 앱 리로드 | 모듈 캐시·플래그 초기화 |
| 2. 아무 단어나 재생 | **무음** + `[audio] 단어 'OOO' 재생 에러: Source error` |
| 3. **같은 단어** 다시 재생 | **소리 남** ✅ |

**판정 기준을 로그가 아니라 3단계의 소리로 잡은 것이 중요합니다.**
수정 전이라면 3단계도 무음이어야 했습니다. 소리가 났다는 건 **다른 플레이어가 만들어졌다**는 뜻이고,
그건 죽은 것이 `playerCache`에서 빠졌다는 직접 증거입니다.

임시 코드는 검증 후 전부 제거했습니다 (`git grep`으로 흔적 없음 확인).

## 7. 무엇이 좋아졌나

| | 수정 전 | 수정 후 |
|---|---|---|

**바뀐 건 "반복"이지 "첫 실패"가 아닙니다.** 첫 3초는 그대로 남아 있습니다.

## 8. 남은 것

**첫 실패의 3초를 0으로 만들 수 있습니다.**
에러 분기에서 `handlePlaybackComplete(onComplete, currentPlaybackId)`를 부르면 됩니다(1줄).
ExoPlayer의 `onPlayerError`는 종료성 에러라(플레이어가 IDLE로 떨어짐) 3초를 기다려도
그 재생이 되살아날 일은 없습니다. **기다림이 순수한 헛시간입니다.**

이번엔 **안 했습니다.** 이유:
- 이득이 작습니다 — 드문 실패 × 한 번 × 3초. 아픈 쪽(반복)은 이미 해결됨
- 검증 비용이 붙습니다 — "재생 도중 에러"에서 정상 재생을 자르지 않는지 따로 봐야 함
- 커밋 성격이 섞입니다 — 지금 세 파일은 "죽은 플레이어 축출" 한 가지만 합니다

**그 외**
- `Source error`의 근본 원인은 미해결 (→ `audio-무음-원인과-방향.md` 13-2)
- 드럼 탭(`context/AudioManager.tsx`)에 같은 문제가 있는지 확인 안 함
